# Kinematic 이동·충돌 테스트 케이스

이 문서는 Kinematic의 우선순위, 초기 겹침, Sweep, Discrete를 확인할 때 사용할 시나리오와 기대 결과를 기록한다. 결과는 2026-10-18 소스 감사와 격리된 Unity/.NET 검증을 바탕으로 정리했다. 전체 과거 입력을 빠짐없이 재검사한 목록은 아니며, Unity 원 프로젝트의 Battle1 Play 모드 전체 동작을 보증하지 않는다.

2026-10-21 기준으로 상태 소유권과 Smooth 보정 설명을 갱신했다. 과거 집계는 검사 당시 기록으로 유지하며, 최근 검증은 아래 별도 항목으로 구분한다. 현재 Discrete·Initial에는 보정 경로 Cast나 막힘 기록이 없으므로, 과거 벽 연쇄 통과 수치를 최신 소스 전체의 검증 결과로 해석하지 않는다.

## 테스트 준비

- 바디는 `KinematicDynamicMoveTest` 또는 동일한 `KinematicBody` 설정을 사용한다.
- 별도 언급이 없으면 충돌 크기는 원 반지름 `0.5`, 박스 half extents `(0.5, 0.5)`로 맞춘다.
- 우선순위는 `Low < Medium < High` 순서다. 정적 바디는 움직이지 않는다.
- 정적 바디가 QuadTree의 월드 Bounds 안에 들어오는지 확인한다. Bounds 밖에 삽입된 정적 바디는 쿼리 결과에 나오지 않아 충돌 후보가 되지 않는다.
- Sweep과 Discrete 결과를 비교할 때는 같은 시작 위치, 형상, 우선순위, 등록 순서, 요청 이동량을 사용한다.
- 겹침 판정은 `TryCollide`의 허용 오차를 고려한다. 아래 자동 검사 집계의 잔여 겹침 기준은 침투 깊이 `0.00002` 초과다.

## 2026-10-21 상태 소유권 검증과 Smooth 확인 항목

`KinematicCorrectionState` 제거 당시 복사한 Data·Interface·Runtime과 CustomAttributes Runtime을 별도 Unity 6000.3.21f1 프로젝트에서 컴파일했다. 원본 프로젝트 배치 실행은 다른 Editor가 열려 있어 차단됐고, 별도 프로젝트는 종료 코드 0과 `STATE_OWNERSHIP_PASS: 16 assertions (Discrete and Sweep)`를 기록했다. 원본 Battle1 Play 모드는 검증하지 않았다.

| 구성 / 입력 | 기대 결과 | 확인된 결과 |
| --- | --- | --- |
| Discrete·Sweep 각각 빈 목록으로 시작하고 High 원 `x=0`, Low 원 `x=2`, 반지름 1을 추가. High에 `+1` 입력 | High `x=1`, Low `x=3`으로 밀림 | 두 모드 통과 |
| 위 Solve 다음 Low에 `-0.5` 입력, High는 정지 | Low가 원래 우선순위로 시작하여 High를 밀지 않고 `x=3` 유지 | 두 모드 통과 |
| Low 제거 후 High에 `+1` 입력, 이후 목록을 비우고 재실행 | High `x=2`, 인덱스·빈 목록 오류 없음 | 두 모드 통과 |
| Low 원 `x=-0.5`, High 원 `x=1.5`, 반지름 1. 벽 중심 `x=-2`, half extents `(1,1)`. Initial만 호출 | 벽 권한으로 Low `x=0`, High `x=2`. Initial 종료 시 우선순위 버퍼 Count 0 | 두 모드 설정에서 통과 |
| Smooth 0.1초 ease-out에서 새 Initial 보정과 재보정 | anchor는 즉시 보정되고 표시 오프셋만 감속하며 감소. 재보정은 남은 오프셋을 합산하고 경과 시간 재시작 | 현재 소스 대조만 수행. 실제 프레임별 표시·완료 시간의 Play 모드 검증은 미수행 |

이 16개 assertion은 제한된 상태 분리 회귀 검사다. 전체 연쇄·무작위 배치 재검사나 이후 ease-out 변경의 시각적 검증을 포함하지 않는다. Sweep은 `SweepBodyState.PushPriority`, Discrete는 `DiscreteBodyState.PushPriority`로 이동 중 승계를 계속 수행한다.

## P-10 동시 정지 접촉 회귀 검사

반지름 `0.5`인 High 원을 `(-1.0466622, 5)`, `(-0.046668813, 5)`, `(0.95333123, 5)`에 놓고, 이동 주체 원을 `(-0.54666555, 5.8660274)`에 놓는다. 이동 주체의 우선순위는 Medium과 High를 각각 검사한다. 이동 주체를 포함한 네 바디의 등록 순서 24가지마다 새로운 상태에서 Sweep을 실행하고, 매 프레임 `(±0.047140453, -0.047140453)`을 30프레임 요청한다. 이 검사는 Initial 단계 반복 횟수를 늘리는 검사가 아니라 매 프레임 최상위 `Solve()`를 호출하는 이동 검사다.

기대 결과는 첫 프레임에 입력 방향으로 X가 `0.01` 이상 진행하고, 30프레임 후 `0.8` 이상 진행하며, 같은 입력 방향·우선순위에서 등록 순서를 바꿔도 최종 좌표 차이가 `1e-5` 미만인 것이다. 최종 원끼리의 actionable overlap도 없어야 한다. 수정 전에는 오른쪽 입력의 첫 프레임 진행 검사가 실패했고, 수정 후에는 이 조건을 모두 통과했다.

추가로 정적 원의 삽입 순서 교환, 닫힌 코너의 정지와 무관한 바디의 이동 유지, 중복 접촉 및 후속 벽, 움직이는 동급 바디 쌍, High→Low→Medium 밀림을 포함하여 112개 시나리오·412개 assertion을 검사했다. 최신 소스와 동일한 파일 해시의 Kinematic Data/Interface/Runtime 및 CustomAttributes Runtime을 격리 Unity 6000.3.21f1 프로젝트에서 컴파일하여 오류 없이 종료 코드 0을 확인했다. 실제 Battle1 Play 모드 검증은 수행하지 않았다. 저장된 설정이 Discrete이면 이 Sweep 수정 경로를 실행하지 않으므로 수동 재현 시 Collision Detection을 확인해야 한다.

## Discrete 반복 한도와 연쇄 보정

현재 [KinematicDiscreteSolver](../Runtime/KinematicDiscreteSolver.cs)는 이동 요청을 먼저 전부 적용한 뒤, 정적 충돌 보정과 동적 쌍 보정을 한 회차씩 실행한다. `MaxSolverIterationCount`는 이 **이동 후 겹침 해소 반복 수**이며 현재 값은 `16`이다. 한 회차 안에서 정적 바디 검사 후 동적 바디 쌍 검사를 수행하고, 충돌이 더 이상 없으면 일찍 끝낸다.

한 쌍을 보정하면 그 바디가 다른 바디와 새로 겹칠 수 있다. 앞에서 이미 검사한 쌍에 새 겹침이 생기면 다음 회차에서 다시 검사해야 한다. 따라서 반복 한도가 낮으면 연쇄의 일부만 이번 Solve에서 반영되고, 마지막에는 겹침이 남을 수 있다. 한도를 올리면 더 많은 재검사 기회를 주지만, 바디 수와 접촉 구조만으로 필요한 회차를 정확히 정할 수는 없다. 한 회차 안에서 뒤에 있는 쌍으로 겹침이 전달되면 다음 반복 전에 일부 연쇄가 진행되기도 하고, 등록 순서나 보정 방향에 따라 같은 회차 수의 결과가 달라질 수 있다.

`16회 = 16개 바디` 또는 `16회면 모든 연쇄를 해결`이라는 의미가 아니다. 반복 횟수는 안전한 바디 수가 아니라 한 프레임 안에서 보정을 다시 검사하는 상한이다. 감사에서는 반복 수를 늘려도 특정 대각선 3바디 보정 반복이 해소되지 않는 사례도 확인했다. 그러므로 잔여 겹침을 볼 때는 긴 연쇄가 단순히 반복 한도를 다 썼는지와, 같은 접촉들이 서로 보정을 되돌리는 순환 상태인지 구분해야 한다.

초기 겹침 단계는 별도 솔버 루프이며 현재 [KinematicSolver](../Runtime/KinematicSolver.cs)의 반복 한도는 `2`다. 이 값과 Discrete 이동 후 보정의 `16`은 서로 다른 단계의 설정이다. Discrete 이동량이 0이면 이동 후 단계가 쌍 검사를 건너뛰더라도, Solve 시작의 초기 겹침 처리는 별도로 실행된다.

반복 한도 변경을 비교할 때는 동일한 씬과 등록 순서로 `1, 2, 4, 8, 16`회를 실행하고, 매 실행에서 최종 바디 좌표, 남은 접촉 쌍과 침투 깊이, 처리 시간을 기록한다. 기대 결과는 한도에 따라 재검사 기회와 비용이 달라지는 것을 관찰하는 것이다. 한도 증가가 모든 배치의 잔여 겹침을 반드시 단조롭게 줄인다고 가정하지 않는다.

## 이전 자동 검사 집계

2026-10-18 감사에서 격리된 Unity 프로젝트와 .NET 하네스로 아래 묶음을 실행했다. 개별 기대 결과는 위 기능 테스트에 적었다.

| 검사 묶음 | 입력 규모 | 관찰 결과 |
|---|---:|---|
| 미세 Sweep 접촉, 초기 우선순위 승계, 벽 승계 범위, Discrete 이동량, 밀림 후 슬라이드 | 479 시나리오 | .NET 및 격리 Unity 검증 통과, 누적 assertion 186,918 |
| 정지한 High와 Medium→Low 연쇄 | 144 | 통과 |
| 벽 앞 4바디 연쇄, 방향·좌표·등록 순서 변화 | 192 | 통과 |
| 혼합 도형 및 단일 프레임 구조화/무작위 입력 | 10,844 | 10,664 통과, 180은 감수하기로 한 긴 Discrete 연쇄 한도 관련 잔여 겹침 |
| 같은 무작위 배치를 60프레임 반복 입력 | 1,000 | Sweep 500은 잔여 겹침 없음. Discrete 500 중 69개 입력에서 동적/벽 잔여 겹침이 한 번 이상 검출됨 |
| 초기 겹침 체인 길이·도형·우선순위·등록 순서·벽 유무 | 288 | 복잡한 일부 배치에서 한 번의 초기 Solve 뒤에도 겹침이 남음 |
| 같은 시점 원 다중 접촉의 대각선 슬라이딩 | 112 | 당시 일부 실패. 2026-10-20 정지 표면 동시 접촉 수정 후 재검사는 P-10 참고 |

이 집계는 모든 무작위 입력을 실제 Unity에서 실행했다는 뜻이 아니다. 격리 Unity 검증과 .NET 검증의 범위가 다르며, Battle1 전체 입력·Pawn·PlayerLoop를 Play 모드로 검증한 결과도 아니다.
